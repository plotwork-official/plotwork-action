# Contributing

Issues are welcome. Most changes cannot be made here by pull request, for the reason below.

## Where the source lives

The action's source and the diagram engine are in a private Plotwork monorepo. Its build bundles them into `dist/index.js`, writes `action.yml`, `LICENSE`, and `dist/licenses/`, and redraws `test/fixtures/in-sync`. Those files are generated, so an edit to them here would be overwritten by the next release.

| Path | Edited here? |
|---|---|
| `dist/`, `action.yml`, `LICENSE` | No. Generated by the monorepo build. |
| `CHANGELOG.md` | No. Written from the monorepo's changelog with each release. |
| `README.md`, `SECURITY.md`, `CONTRIBUTING.md`, `examples/` | Yes. |
| `.github/` | Yes. |
| `test/fixtures/` | Yes, except the SVGs and picture blocks in `test/fixtures/in-sync`, which the build redraws. |

## Issues

Open an issue for a bug, a confusing message, or a feature request. For a bug, include:

- the release you used (`v1`, `v1.2.0`, or a commit SHA);
- the workflow step, with its inputs;
- the log of the step, with the annotations;
- the smallest diagram or Markdown file that shows it.

Report a vulnerability privately instead, as [SECURITY.md](SECURITY.md) describes.

## Pull requests

A pull request that fixes the documentation, an example, a workflow, or a fixture is welcome. For a change to the action's behaviour, open an issue first; the fix is made in the monorepo and arrives here in a release.

## Releases

Nobody commits or tags here by hand. The monorepo's release workflow does it with a GitHub App:

1. A change to the action or the engine reaches the monorepo's `preview` branch. The workflow tests it, builds `dist/`, `action.yml`, and `test/fixtures/in-sync` into a clone of `next`, and pushes one commit named after the monorepo commit.
2. CI here runs every command against `test/fixtures` and checks `dist/` against `dist/checksums.txt` on that commit.
3. When the version is a new beta and CI passed, the workflow tags `vX.Y.Z-beta.N` and publishes a GitHub release marked pre-release, with notes from `CHANGELOG.md`. `v1` does not move.
4. A stable version reaches the monorepo's `main`. The same steps run against `main` here, then the workflow tags `vX.Y.Z` and publishes it as the latest release.
5. `release.yml` checks the stable tag is on `main` and moves the major tag `vX` to it. It is the only thing that moves a major tag.

Edits to the files marked "Yes" above go to `main`, by pull request. The next build merges `main` into `next`.
